# OmniEdit Baseline 评测执行规范与事故复盘

本目录用于在冻结的 OmniEdit 对齐子集上评测 Lance、VACE、Bernini 等视频编辑模型，并制作人工审核包。本文件记录 2026-09-26 至 2026-09-27 执行中暴露的问题，以及后续运行必须遵守的原则。

## 核心原则

> 只防止已经发生过、或能够明确证明会破坏结果的问题。不要用推测性的“保险检查”阻塞昂贵推理。

> 生成阶段宽进，审核交付阶段严出。尽量保留结果并继续；宁愿先生成出可能有问题的结果，也不要让单条异常退出整个批次。

> 异常默认记录为 warning，而不是 raise。推理、技术验收、统一转码和审核包制作必须解耦。

具体含义：

- 推理阶段的首要目标是在有限 GPU 时间内尽可能多地生成结果。
- 非致命异常必须写入 manifest/log，并继续下一条样本。
- 严格的尺寸、编码、像素格式、命名和审核页面检查放到推理完成之后；能转码修复的问题不得触发重新推理。
- 单条失败不得中断同一批次的其他样本，也不得影响其他 GPU 分片。
- 已生成的视频优先保留。即使后续判定不适合交付，也应作为诊断产物存在，而不是静默删除。

## 本次事故

### VACE：正确的竖屏输出被错误校验终止

VACE 已完成全部 24 条 Tier A mask。前两条正式输出成功；第三条竖屏样本 `Sp_Color_change_02` 也已经完成 40 步推理并编码为 81 帧视频。

失败原因不是模型推理，而是 runner 将名义尺寸配置 `480×832` 当成实际输出尺寸。VACE 的 stride 对齐预处理实际产生 `464×848` conditioning 和输出。脚本在完整视频生成后执行固定尺寸相等检查，误判结果无效并抛出异常，导致后续 21 条任务没有运行。

教训：

- 配置标签不是实际媒体规格，必须以 conditioning 或生成文件实测值为准。
- 尺寸、帧率或帧数与预期不同，应记录 warning 并保留视频，不应终止批次。
- 临时视频只要能够完整解码，就应保留并在恢复时优先转正，不能无条件重算。
- landscape smoke 成功不能代表 portrait 分支成功；但 smoke 覆盖不足也不应通过增加硬退出条件来“补救”。

### Bernini：不存在的文件条件导致空等至作业超时

Bernini 的约 126 GB 权重和运行环境在旧节点上已经完整下载，两个 transformer 各 12 个分片、text encoder 3 个分片均存在，残留 `.incomplete` 文件数为 0，环境导入也成功。

等待脚本却额外要求模型根目录存在未经官方布局确认的 `model_index.json`。真实仓库不满足这个附加条件，因此脚本在权重完整后仍每 30 秒空等，始终没有进入 smoke，最终随 18 小时 Slurm 作业超时退出。

教训：

- 不得臆测模型仓库必须存在某个可选文件。
- 下载成功应以官方下载命令退出码、索引引用的必需分片、以及一次实际模型加载为依据。
- 当下载进程已经成功结束、分片齐全时，应直接尝试加载；加载失败再记录真实错误，不能继续无限等待猜测条件。
- 所有等待循环都必须输出“为什么仍在等待”，并设置合理期限。期限到达后写入明确失败状态，而不是耗尽整个 GPU 作业。

### 运维：脱离会话不等于无人值守可靠

推理被放入 detached Slurm step 后能够脱离 Codex 会话继续运行，但没有针对“批次提前退出”和“完成条件永远不成立”设置恢复策略或明确告警。因此进程形式上无人值守，实际上一个提前失败、一个无效等待。

另外，模型和环境按照约定放在节点本地 `/tmp`。作业超时释放节点后，可重建缓存随节点丢失；共享 scratch 中的 mask、输出、manifest 和日志得以保留。节点本地缓存本身不是错误，但必须把重新下载时间纳入资源预算。

## 后续实现规范

### 1. 推理只设置最小硬阻塞条件

允许硬阻塞的情况仅限：

- 必需输入文件不存在或完全无法解码；
- 模型权重无法加载，因而根本不能开始推理；
- GPU OOM、CUDA/NCCL 崩溃等使当前任务无法继续；
- 磁盘写满或输出无法落盘；
- 已经实际发生过、且能够明确证明继续运行必然破坏全部结果的问题。

即使出现上述问题，也应优先只标记当前样本或当前分片失败。除非所有后续样本必然同样失败，否则不得终止整个批次。

以下情况默认只能产生 warning：

- 输出分辨率与配置名称不同；
- 帧数、帧率、时长、码率或像素格式偏离审核包目标；
- 可选元数据或未被官方要求的文件不存在；
- mask 面积、模型效果或编辑符合度看起来可疑；
- 后置技术验收失败但视频仍可解码。

### 2. 单样本隔离，失败后继续

每条任务必须独立处理并落盘状态：

- `generated`：生成完成；
- `generated_with_warnings`：视频可用，但存在技术或内容异常；
- `failed`：当前样本无法生成；
- `reused`：复用已有正式输出；
- `recovered_tmp`：复用完整临时输出。

单条任务捕获异常后，将异常类型、消息、时间和日志路径写入 manifest，然后继续下一条。四卡并行时，每个分片独立推进，任何一个分片失败不得取消其他分片。

### 3. 产物优先，恢复优先

恢复顺序固定为：

1. 正式输出能够解码：直接复用；
2. `.tmp.mp4` 能够完整解码：原子转正并标记 `recovered_tmp`；
3. 文件存在但部分损坏：保留原文件并改名归档，再重新推理；
4. 文件不存在：执行推理。

不要因为 manifest 缺字段、尺寸不符合审核包规格或后置校验失败而重新运行昂贵推理。此类问题应在后处理阶段修复。

### 4. 推理与审核严格解耦

流程分为两个边界清楚的阶段：

1. **生成阶段**：接受模型实际输出，记录原始规格和所有异常，最大化完成数量。
2. **审核交付阶段**：统一转码为 H.264、`yuv420p`、faststart，检查离线 HTML、标签字段、ZIP 单顶层目录、CRC 和 SHA256。

审核阶段可以拒绝某个文件进入最终 ZIP，但不得反向导致整批推理退出。需要补跑时，根据 manifest 生成明确的补跑清单。

### 5. 完成条件必须来自事实

模型下载完成条件按以下优先级判断：

1. 官方下载命令成功退出；
2. 官方索引中引用的权重分片全部存在；
3. Python 能够实际构造模型或 pipeline；
4. smoke 能够生成至少一个视频。

不要检查官方没有承诺的目录名、附加 JSON 或自行猜测的 sentinel。自建 `.done` 文件只能在对应命令成功退出后写入，不能代替真实加载测试。

### 6. Smoke 只用于发现兼容性问题

在资源允许时，smoke 至少覆盖：

- 一个横屏样本；
- 一个竖屏样本；
- Bernini 的 `v2v` 路径；
- Bernini 的 `mv2v` 路径；
- 保存、临时文件恢复和最终解码。

Smoke 发现的差异应首先转化为兼容逻辑或 warning，不应轻易增加新的硬退出条件。正式批次仍必须具备逐条容错能力，不能假设 smoke 覆盖了所有情况。

### 7. 等待和监控必须观察进展

长时间任务至少记录：

- 当前阶段；
- 已完成/总任务数；
- 最近一次进展时间；
- GPU 是否实际有计算进程；
- 等待某个条件时，该条件的具体当前值；
- 预计的 Slurm 剩余时限。

如果权重完整而等待条件仍不满足，应尝试真实加载并记录错误。禁止在没有进展的情况下循环到作业超时。

### 8. 资源时限内优先提高完成率

- 可独立运行的单卡模型应按 GPU 分片并行，而不是默认串行。
- 先生成冻结 Tier A 子集，再考虑扩展 Tier B。
- 预留模型下载、首次编译、转码和打包时间。
- 节点本地缓存消失是可预期事件；正式结果、mask、manifest、日志和审核包必须始终写入共享 scratch。
- 不为追求“所有检查全绿”牺牲大量可生成样本。

## 本轮正式运行补充结论

- **VACE**：24 条均实际传入 `source_conditioning.mp4 + mask.mp4`；保留 mask、overlay 和哈希。目的区域联合 mask 不强制满足局部面积阈值。
- **Bernini/H200**：四卡上 `--ulysses 1`（DP4、单卡一条）吞吐最佳且无 OOM；`--ulysses 2` 仅作显存回退，FSDP2 不用于推理。
- **持久化**：环境和模型可放 `/tmp`，输出必须用 `/scratch` 绝对路径逐条落盘；相对路径曾导致 23 条结果随节点本地盘丢失。
- **上传**：bypy 分片若报 31064，改用直连和 `-s 200m` 整文件上传，并以 `bypy meta` 核对大小与 MD5。
- 最终 VACE、Bernini 各完成对齐 Tier A 24/24，与 Lance 共三个审核包，已上传至 `/apps/bypy/lance_review/omni_baselines_20260926/`。

## 提交无人值守任务前检查表

- [ ] 单条失败只写状态，不会退出整个批次。
- [ ] landscape 与 portrait 都能被接受，实际尺寸不靠配置名猜测。
- [ ] 已有正式输出和完整 `.tmp.mp4` 均可恢复复用。
- [ ] 下载完成条件来自官方命令、权重索引或真实加载。
- [ ] 没有未经验证的可选文件硬条件。
- [ ] 等待循环能够检测进展停滞，并在合理时间转入真实加载或明确失败。
- [ ] 多 GPU 分片互不取消。
- [ ] 严格媒体规范仅在审核包阶段执行。
- [ ] 所有 warning、失败和复用行为均进入 manifest。
- [ ] 正式产物保存在共享 scratch，而不是仅存在节点 `/tmp`。

最终判断标准不是“脚本是否足够谨慎”，而是：在不破坏已有结果的前提下，是否用有限算力生成了最多可审阅的视频，并留下足够信息供后续筛选、修复和补跑。
